## Notes

Local numbers come from a laptop (i9-13900H under WSL2, turbo on) shared with other work, so they
only compare two binaries run alternately (`hyperfine`) and read the cgroup `memory.peak` the way the
board does. The same commit measured twice on the board moved between 0.0606 and 0.0736 s, so small
differences in T are noise; M and S are stable.

**Step 1.** The file is mapped, never copied: the board pre-warms it into the page cache, so a mapping
costs no memory of our own, where reading it into a buffer would cost its 239 MB. Every timestamp is
27 bytes, so the hour is the first 13 bytes; it is recomputed (integer calendar arithmetic, no date
library) only when that prefix changes, which is rare because each shard writes in time order.
Percentiles use `select_nth_unstable` on three shrinking prefixes instead of sorting each group.

**Step 2 - memory.** Step 1 parsed into packed records, then counted per group and copied every
latency into a group-ordered array: three per-line arrays alive at once. Rewriting each record in
place as `group << 33 | 5xx << 32 | latency` and sorting it per chunk leaves one per-line array; the
output walks the groups across the 12 sorted chunks. Local peak 39 MiB; board 74 -> 42.5 MB and
0.088 -> 0.072 s, with 48 fewer lines.

**Step 3 - the parse.** A local profile put the parse at most of the time (60-85 ms of ~140 ms,
loaded laptop), at about 230 ns per 77-byte line. Spaces are now found 8 bytes at a time (the classic
zero-byte test on `word ^ 0x2020...`, exact for the first match), endpoints are interned in an
open-addressing table that compares a stored hash before the bytes instead of `HashMap::entry`, and the
hour range is tracked while parsing instead of in a serial pass over 3.1M records. A/B 1.22 +/- 0.19x;
board 0.071 -> 0.061 s.

**Step 4 - no library calls per line.** `perf` (installed in WSL for this) put ~25 % of the time in
unresolved libc addresses: `memcpy` from hashing with `chunks(8)` + `copy_from_slice`, and `memcmp` for
endpoint equality. Both became masked 8-byte unaligned loads (an endpoint is always followed by at least
7 bytes of its line, so the reads stay in the mapping). User CPU 557 -> 412 ms in the A/B.

**Tried and dropped.**
- Copying endpoints into a per-thread arena with tagged slots, because `perf annotate` put 39 % of the
  lookup on loading the stored key from its first occurrence in the 239 MB map: `perf stat` task-clock
  966.65 ms against 967.86 ms over 15 runs. The hot spot moved; the total did not.
- An in-place radix partition (American flag sort) on the group's top 8 bits before sorting each
  bucket: task-clock 966 -> 1044 ms. `sort_unstable` on 260k `u64` per thread is already cache-friendly.

**Step "latencies as u32" (19d64ca).** After each chunk is sorted by `(group, 5xx, latency)`, its
latencies are written two per u64 into the front of the same buffer (latency i lands inside record
i / 2, which has already been read), the buffer is truncated and shrunk to half, and each group keeps
one `[group, start, end, 5xx count]` run. The output's page cache is charged to the run, so the
latencies are dropped before it is written and each part is freed once written. Local cgroup peak
41 -> 28 MiB at the same CPU time (interleaved, n = 10); board 40.8 -> 33.5 MiB, S 310 -> 332.

**After a restart, 31 Oct.** Phase timer (local, busy host): parse ~55 % of wall, sort ~22 %, format
~7 %, final write ~8 %.

**Cheaper per-line parse (55c8cb5).** The 13-byte hour prefix was a slice comparison (a libc call), now
two overlapping 8-byte words; the latency is read 8 bytes at a time (SWAR end test, digits combined
pairwise); the endpoint hash uses only the first and last 8 bytes and the length instead of a
dependent multiply per 8 bytes (equality is still checked in full). Laptop CPU 0.88x. Board, three runs
of this code: 0.0622, 0.0515, 0.0513 s (A's spread on identical code is large).

**Sort by group only (fde07bb).** Percentiles are selected later, so latency order inside a group is
not needed: sorting by the group alone gives pdqsort many equal keys. Board 0.0489 s, 73.0 points.

**Memory in every phase (80405f3).** Anonymous RSS was flat at 26-28 MB: all packed records during the
parse and sort, then latencies (12.4 MB) plus the output text (10 MB) while formatting. Each thread now
parses its chunk in 4 MB pieces, sorting each piece by (hour, local endpoint) and reducing it to u32
latencies and runs before reading the next; runs get their global group after the merge. Statistics
are computed per group first and the latencies freed before any text exists. A first version kept a
run vector per piece, and those small freed vectors stayed resident; one vector per thread fixed it.
Phase peaks 19 / 21 / 19 MB; board M 33.1 -> 26.0 MB.

**Tried and dropped (31 Oct).** `MAP_POPULATE` on the input: populating the mapping costs ~15 ms
serially, about what the parallel page faults cost inside the parse.
