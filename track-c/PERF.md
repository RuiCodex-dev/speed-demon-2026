## Notes

Local numbers come from a laptop (i9-13900H under WSL2, turbo on) shared with other work; they only
compare two binaries run alternately (`hyperfine`, user CPU) and read the cgroup `memory.peak`.

**Correctness first.** The spec is stricter than Python's `csv` module: quotes appear only in quoted
fields and `""` escapes come in pairs, so a byte is inside quotes exactly when an odd number of `"`
precede it. Twelve threads count quotes per chunk, a prefix parity tells every cut whether it sits
inside a quoted field, and each chunk starts after its first line break outside quotes. Byte counts are
the raw length minus one per `""`, so text is unescaped only for names that need it.

**Step 1 -> 2.** A phase profile of step 1: regions 27 ms (sorting 200k slices), chunking 13 ms (96
counting threads, oversubscribed), parse 128 ms, and a serial merge of the 12 per-thread name tables
155 ms. Partitioning names by hash and merging each partition on its own thread, a one-pass regions
reader and 12 counting threads gave board 0.334 -> 0.165 s, but memory rose to 139 MB.

**Step 3 - where the time really was.** With name interning removed (an experiment that fails the hash),
user CPU fell from 2.1 s to 0.55 s: three quarters of the work was looking names up in 12 per-thread
tables of ~100k entries and comparing bytes at random places in the 200 MB map. Each record now appends
(country, unescaped name) to a buffer per name partition - sequential writes - and each partition owner
interns only its own few thousand names in a table that stays in cache. A/B user CPU 2.4 -> 0.9 s;
board 0.165 -> 0.109 s, 139 -> 69 MB.

**Step 4 - nothing per record.** The leaders' memory (about 10 MB) showed per-record buffers were the
next cost. Now one lock-free table shared by all threads maps a name to an id (slot = hash tag and
id, compare-and-swap insert), each distinct name is copied once into a compact arena so the exact byte
comparison stays in cache, and each record sets one atomic bit (country, id). The table is sized for
the spec's pool of 100,000 names but does not rely on it: if it fills, the run repeats with a table four
times larger. The large arrays come from `calloc`, so pages that are never written cost nothing.
Board 69 -> 38 MB; T rose from 0.109 to 0.122 s (shared cache lines), and K still went up (13.3 -> 14.0).

**Step 5.** `perf` again: 13 % in libc (`memcpy` in the hasher, `memcmp` in the comparison). Names are now
hashed and compared with masked 8-byte loads - a name is followed by at least 10 bytes of its record,
and arena copies carry 8 bytes of padding - and quotes are found 8 bytes at a time. Board 0.122 -> 0.102 s.

**Step 6 - a local win the board refused.** `perf annotate` showed three misses per name lookup (arena
bytes 43 %, the id's span 22 %, the slot 18 %). Using the slot index itself as the id removed the span
array and was 1.13x faster on the laptop, but the board measured 0.1016 -> 0.1081 s and 39.9 -> 44.7 MB:
bitsets indexed by slot are 2.6x larger, and the scoring CPU has 1.25 MB of L2 per core against the
laptop's 2 MB. Reverted the next commit. The board is the only judge of a memory-layout change.

**Step 7.** The same miss removed without the bigger bitsets: the slot packs `tag | id | arena offset`
and the name's length is stored in front of its bytes, in the same cache line. Interleaved A/B: CPU -16 %.

**Step 8.** The region -> country lookup was 29 % of the parse loop: a random read of a 2 MB `u16`
array. With fewer than 255 countries it is now one byte per region, 1 MB, which fits L2; `parse` is
generic so a larger input still gets the `u16` map. CPU -10 % on the laptop.

**Transparent huge pages (68a80a0).** The board read about 25 MB more than a local cgroup (15 MiB
locally, 41 on the board). Two guesses failed on the board: 256 KB thread stacks (6c0adb6) and a
single malloc arena (a42994e). Setting THP to `always` on the laptop for one measurement (then back
to `madvise`) reproduced it, 15 -> 24-28 MiB, and `prctl(PR_SET_THP_DISABLE)` at the start of main
brought it back to 15. Board: 41.0 -> 16.8 MiB at the same T, 58.7 -> 63.5 points. The same call
made B and D slower on the board (huge pages help their random access) and did nothing for A, so
only C keeps it.

**Two records in flight (46bd27f, 99f6d1c).** The parse loop keeps one parsed record pending: while
the next record is parsed and hashed, its name-table slot and region->country entry are prefetched,
and the pending one is counted. Laptop CPU 0.848x. Deeper pipelines (also prefetching the arena entry
and the bitset word: 0.985x of this) and re-parsing to peek ahead (1.17x) did not pay. 99f6d1c
expressed the same thing in fewer formatted lines (the bitsets moved into the name table).
