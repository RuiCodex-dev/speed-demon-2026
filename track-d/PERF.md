## Notes

Local numbers come from a laptop (i9-13900H under WSL2, turbo on) that other workloads kept busy,
so they are only used to compare two binaries run alternately (`hyperfine`, user CPU time) and to
read the cgroup's `memory.peak` the way the board does. The board decides.

**Step 2 - the tail was the queries that cannot succeed.** After step 1 a per-query timer showed the
build at 0.10 s and the queries at 1.3 s. The spec's "unreachable, no-in target" queries ask for a node
that has no in-edge: Dijkstra proves that by exploring the whole 1.74M-node graph. A bitset of nodes with
an in-edge from another node (self-loops do not count) answers them before any search. Local 2.31 -> 1.41 s.

**Step 3 - locality.** With the tail gone, 70 queries still took over 50 ms each, about 600 ns per
settled node: node ids are a random relabelling, so every distance, offset and edge access missed the
cache. Renumbering nodes in breadth-first order (Cuthill-McKee style) puts a search's neighbourhood in
nearby memory. The BFS cost 160 ms (serial) and still halved the total: local 1.4-1.7 -> 0.71-0.74 s.

**Tried and dropped - hash-table distances.** A per-search open-addressing table instead of an n-sized
array per thread cut peak memory to 149-169 MiB but made the run 1.49x slower (1.06-1.09 s against
0.69-0.74 s): hashing threw away the locality the renumbering had just bought.

**Step 4.** A three-pass build (degrees, CSR in input ids for the BFS, then a third parse scattering
straight into the renumbered CSR) avoided keeping two edge lists; a radix heap replaced `BinaryHeap`
(Dijkstra's keys are monotone): user CPU 9.1-11.8 s -> 6.8-8.7 s in the A/B.

**Step 5.** The BFS runs from 12 seeds at once, each thread claiming nodes with an atomic flag, so
each region gets contiguous ids; nodes no seed reaches are numbered afterwards. A/B 1.61 +/- 0.32x.

**Step 6 - memory.** Distances are stored as `u32` "distance + 1" in calloc'd arrays: 0 means
unreached, so the arrays need no initialisation and untouched pages cost nothing, and they are half the
size. The spec has distances above 2^32; a search that would overflow returns an error and is repeated
exactly with a `u64` array allocated on first need. One generic function serves both. Peak 256 -> 182 MB.

**Step 7 (pending on the board).** The build was three passes of random atomic updates over node-sized
arrays: ~15M cache misses each. Now one text parse files every edge into a bucket by tail id
(`u >> 13`, about 8k nodes) with sequential writes, each thread marks in-edges in its own 218 KB bitset,
and each bucket is counting-sorted into its slice of the CSR inside the cache. Regrowing the bucket
vectors showed up as system time (0.69 -> 1.71 s) until they were pre-sized from the chunk length.
A/B 1.58 +/- 0.40x.

**Step 8 - queries in source order.** A per-phase timer (quietest local run): parse 34 ms, CSR 17, BFS
55, renumbered CSR 44, queries 264. Taking the queries in order of their source's new id makes the 12
threads search neighbouring regions at once and share the graph in L3 (-4.9 % CPU), and the serial
pass over nodes no BFS seed reached now loads a flag before it swaps it (wall -4 %). Board 0.319 -> 0.297 s.

**Tried and dropped - bidirectional search, in three rounds.** It settles 42 % fewer nodes (14.3M
against ~24.6M), but the first version was 2.3x slower. `perf` found the reasons one at a time: the
distance arrays were filled instead of coming from calloc; the backward search crosses the spec's
near-2^32 edges and overflowed `u32`, so whole queries were redone in `u64` (fixed by skipping such a
relaxation and repeating only if the answer could depend on it); and "expand the side with the smaller
key" let the backward side sweep the whole graph whenever the forward side started behind a near-2^32
edge (fixed by strict alternation). The final version was 1.14x faster, but the reverse graph and a
second distance array per thread took the peak from 146 to 258 MiB: by the formula
(1.14)^0.5 x (146/258)^0.2 = 0.95, a loss. Kept out.
